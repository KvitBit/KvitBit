## Effect v4.1 and HTTP API conventions

- **Services and layers:** define a `Context.Service` capability; make `Default` acquire dependencies and implement behavior, then expose `Live` by providing the concrete adapter. Tests substitute layers rather than mocking global state. The ARES example demonstrates this end-to-end at [`service.ts:95`](/home/dev/Projects/deskohub/packages/ares/src/backend/service.ts:95) and [`service.test.ts:18`](/home/dev/Projects/deskohub/packages/ares/src/backend/service.test.ts:18). Copy the shape; avoid importing Deskohub’s `runWorkspaceEffect` runners, which are tied to its server lifecycle.
- **Errors:** keep expected failures typed and low-cardinality. `Data.TaggedError` fits internal/provider service errors; HTTP contract errors use `Schema.TaggedError` and carry an `HttpApiSchema.status(...)` annotation so status and schema stay together. Examples: [`service.ts:20`](/home/dev/Projects/deskohub/packages/ares/src/backend/service.ts:20), [`customer-account-api.ts:35`](/home/dev/Projects/deskohub/packages/workspace-customer-api/src/customer-account-api.ts:35), [`customer-account-api.ts:45`](/home/dev/Projects/deskohub/packages/workspace-customer-api/src/customer-account-api.ts:45).
- **HttpApi:** put request/response schemas, endpoint names, methods, paths, and errors in reusable `HttpApiGroup`s, compose groups in an `HttpApi`, and layer auth/origin middleware at the contract boundary. Deskohub’s customer API shows this at [`customer-account-api.ts:554`](/home/dev/Projects/deskohub/packages/workspace-customer-api/src/customer-account-api.ts:554) and [`workspace-customer-api.ts:26`](/home/dev/Projects/deskohub/packages/workspace-customer-api/src/workspace-customer-api.ts:26). The API contract is the useful part to adapt; its `/api/customer` prefix, cookie auth, and origin policy are Deskohub-specific.
