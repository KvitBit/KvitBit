## Facts

**Effect modules and signatures.** Public imports are `effect/cluster/{Entity,Sharding,ClusterCron,SqlMessageStorage,SqlRunnerStorage,SingleRunner,HttpRunner,ClusterWorkflowEngine}` and `effect/workflow/{Workflow,Activity,DurableClock,DurableDeferred}`. In the tarballs, declarations are under `package/dist/cluster/*.d.ts` and `package/dist/workflow/*.d.ts`.

- `Entity.make(type, protocol)` defines an entity and its RPC protocol; `toLayer` registers handlers. `Sharding.layer` requires `ShardingConfig`, `Runners`, `MessageStorage`, `RunnerStorage`, and `RunnerHealth`.
- `ClusterCron.make({ name, cron, execute, shardGroup?, calculateNextRunFromPrevious?, skipIfOlderThan? })` returns a layer. It coordinates initial scheduling through a singleton and persists each run as an entity message. [Entity](https://effect.website/docs/v4/api/effect/cluster/Entity) · [Sharding](https://effect.website/docs/v4/api/effect/cluster/Sharding) · [ClusterCron](https://effect.website/docs/v4/api/effect/cluster/ClusterCron).
- `Workflow.make(tag, { payload, idempotencyKey, success?, error?, suspendedRetrySchedule?, annotations? })`; `Activity.make({ name, execute, success?, error?, interruptRetryPolicy?, annotations? })`; `DurableClock.make({ name, duration })` / `DurableClock.sleep({ name, duration, inMemoryThreshold? })`; `DurableDeferred.make(name, { success?, error? })`. `Workflow.withCompensation(effect, (value, cause) => cleanup)` registers cleanup for a successful top-level effect if the workflow later fails; nested activities are excluded. Completed activity results are memoized, but an external side effect can repeat after a crash before its completion is persisted, so dispatches and writes need idempotency. `ClusterWorkflowEngine.layer` provides the workflow engine from `Sharding` and `MessageStorage`; it persists executions, activity/deferred requests, resume/interrupt messages, and durable-clock wakeups through cluster entities. It creates no separate workflow tables. [Workflow](https://effect.website/docs/v4/api/effect/workflow/Workflow) · [Activity](https://effect.website/docs/v4/api/effect/workflow/Activity) · [DurableClock](https://effect.website/docs/v4/api/effect/workflow/DurableClock) · [DurableDeferred](https://effect.website/docs/v4/api/effect/workflow/DurableDeferred) · [ClusterWorkflowEngine](https://effect.website/docs/v4/api/effect/cluster/ClusterWorkflowEngine).
- Default Postgres tables (`prefix` defaults to `cluster`): **`cluster_messages`** has `id BIGINT PK`, `rowid BIGSERIAL`, `message_id VARCHAR(255) UNIQUE`, `shard_id VARCHAR(50) NOT NULL`, `entity_type VARCHAR(150) NOT NULL`, `entity_id VARCHAR(255) NOT NULL`, `kind INT NOT NULL`, `tag VARCHAR(50)`, `payload/headers TEXT`, `trace_id VARCHAR(32)`, `span_id VARCHAR(16)`, `sampled BOOLEAN`, `processed BOOLEAN NOT NULL DEFAULT FALSE`, `request_id BIGINT NOT NULL`, `reply_id/last_reply_id BIGINT`, `last_read TIMESTAMP`, `deliver_at BIGINT`. **`cluster_replies`** has `id BIGINT PK`, `rowid BIGSERIAL`, `kind INT`, `request_id BIGINT NOT NULL`, `payload TEXT NOT NULL`, `sequence INT`, `acked BOOLEAN NOT NULL DEFAULT FALSE`, and unique `(request_id, kind)` / `(request_id, sequence)`. **`cluster_runners`** has `machine_id SERIAL PK`, `address VARCHAR(255) UNIQUE NOT NULL`, `runner TEXT NOT NULL`, `healthy BOOLEAN NOT NULL DEFAULT TRUE`, `last_heartbeat TIMESTAMP NOT NULL DEFAULT NOW()`. **`cluster_locks`** has `shard_id VARCHAR(50) PK`, `address VARCHAR(255) NOT NULL`, `acquired_at TIMESTAMP NOT NULL`. **`cluster_migrations`** and **`cluster_runner_migrations`** each have `migration_id INTEGER PK`, `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`, `name TEXT NOT NULL`. Migrations create `cluster_messages_shard_idx`, `cluster_messages_request_id_idx`, `cluster_messages_rowid_idx`, `cluster_messages_retention_idx`, and `cluster_replies_request_lookup_idx` (prefix applies). PostgreSQL runner storage uses advisory locks by default. `SqlMessageStorage.layer` and `SqlRunnerStorage.layer` run migrations; 4.1.4 also provides separate migration/storage layers for owner-run DDL and DML-only runtimes. `@effect/sql-pg/PgClient` exports `PgClient.layer(config)` providing `PgClient | SqlClient`. Sources: `package/dist/cluster/SqlMessageStorage.js`, `SqlRunnerStorage.js`, `package/dist/sql/Migrator.js` in the versioned artifact; [SqlMessageStorage](https://effect.website/docs/v4/api/effect/cluster/SqlMessageStorage) · [SqlRunnerStorage](https://effect.website/docs/v4/api/effect/cluster/SqlRunnerStorage) · [PgClient](https://effect.website/docs/v4/api/sql-pg/PgClient).
- `SingleRunner.layer({ runnerStorage?: "memory" | "sql", shardingConfig? })` is single-process mode: no-op runner communication/health, SQL message/reply storage in either runner-storage mode. In 4.1.4 it requires `SqlClient` and `Digest`. For HTTP multi-runner transport, Effect exports `HttpRunner.layerHttp`; Node's adapter is `@effect/platform-node/NodeClusterHttp.layer({ transport: "http" | "websocket", storage?, ... })` plus `layerHttpServer`. There is no module named `ClusterHttp` in these exports. Each `RunnerAddress` is host+port. [SingleRunner](https://effect.website/docs/v4/api/effect/cluster/SingleRunner) · [HttpRunner](https://effect.website/docs/v4/api/effect/cluster/HttpRunner) · [NodeClusterHttp](https://effect.website/docs/v4/api/platform-node/NodeClusterHttp) · [RunnerAddress](https://effect.website/docs/v4/api/effect/cluster/RunnerAddress).

**GCP facts.** Cloud Run session affinity uses a cookie but is best-effort and breaks on instance termination or capacity; internal service calls require an internal VPC route, and IAM-protected calls use OIDC ID tokens. Instance-based billing allocates CPU outside requests, but instances can still terminate; worker pools are URL-less. [Affinity](https://docs.cloud.google.com/run/docs/configuring/session-affinity) · [service authentication](https://docs.cloud.google.com/run/docs/authenticating/service-to-service) · [billing](https://docs.cloud.google.com/run/docs/configuring/billing-settings) · [runtime contract](https://docs.cloud.google.com/run/docs/container-contract). Alchemy documents its GCP cluster pool as Postgres plus Compute Engine runners in a VPC behind a static regional gateway with peer/database firewall rules. [Alchemy Cluster GCP](https://alchemy.run/cluster/gcp/).

## Inference for Kvitbit

- Self-hosted Docker/NixOS: use `PgClient.layer` + `SingleRunner.layer({ runnerStorage: "sql" })` + `ClusterWorkflowEngine.layer`. This keeps workflows durable without intra-runner networking.
- For multi-node GCP, a standard horizontally scaled Cloud Run service URL is not a reliable per-process runner address: Effect routes to each registered host+port, while Cloud Run's service URL fronts instances and affinity is not guaranteed. `NodeClusterHttp` also exposes no Google OIDC option, so auth must be integrated separately. Prefer Alchemy's documented GCP Compute Engine runner pool; a Cloud Run runner topology needs unique reachable endpoint per runner, VPC ingress, OIDC transport, and controlled deployment/scaling.
- Map recurring invoice and daily FX work to `ClusterCron` sweeps that start workflows with idempotency keys including the schedule/currency and billing/rate date. Use reminder workflows with named `DurableClock.sleep`, re-check payment state before dispatch, and `Activity.retry` around Resend with stable idempotency. Use `DurableDeferred` for payment callbacks. Compensation can reverse local reservations/state; it cannot retract an email already sent.
